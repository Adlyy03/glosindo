# PERUBAHAN BESAR ALUR QUICK CHECK-IN/OUT + EVENT

Saya ingin mengubah konsep fitur **Quick Check-in/Out** dan menambahkan sistem **Event** yang terintegrasi dengan data kunjungan.

Jangan hanya menambahkan field `event` ke tabel. Saya ingin alurnya dirancang dengan jelas antara **kunjungan biasa** dan **kunjungan yang terkait Event**.

## 1. KONSEP UTAMA

Saat receptionist melakukan Quick Check-in, harus ada 2 kemungkinan:

### A. Quick Check-in Biasa

Digunakan untuk tamu yang datang seperti kunjungan normal dan tidak terkait event.

Contoh:

* Tamu datang untuk keperluan umum.
* Tamu datang bertemu karyawan.
* Tidak ada event yang sedang diikuti.

Pada kondisi ini:

* `event_id` = NULL
* Kolom Event pada riwayat menampilkan `-`
* Data tetap masuk ke riwayat kunjungan biasa.

### B. Quick Check-in untuk Event

Digunakan ketika tamu datang untuk mengikuti suatu event yang sudah dibuat.

Contoh:

* Meeting
* Seminar
* Training
* Sosialisasi
* Kunjungan perusahaan
* Acara internal
* Event lainnya

Pada kondisi ini:

* Receptionist memilih Event yang sedang berlangsung.
* Kunjungan disimpan dengan `event_id`.
* Kolom Event pada riwayat menampilkan nama event.
* Data kunjungan otomatis masuk ke statistik/laporan event tersebut.

Jadi **Event bukan pengganti kunjungan**, tetapi merupakan kategori/relasi dari suatu kunjungan.

---

# 2. FITUR EVENT

Tambahkan fitur **Event Management** yang dapat digunakan oleh Receptionist.

Receptionist dapat:

* Membuat event
* Melihat daftar event
* Melihat detail event
* Mengubah event
* Menonaktifkan/menghapus event sesuai aturan sistem
* Melihat jumlah peserta/tamu yang mengikuti event
* Melihat laporan event

Data minimal Event:

* ID Event
* Nama Event
* Deskripsi
* Tanggal
* Waktu mulai
* Waktu selesai
* Lokasi
* Status Event
* Dibuat oleh
* Created At
* Updated At

Status event dapat berupa:

* Draft
* Scheduled
* Ongoing
* Finished
* Cancelled

Gunakan status yang paling sesuai dengan struktur aplikasi yang sudah ada.

---

# 3. ALUR RECEPTIONIST MEMBUAT EVENT

Tambahkan menu:

**Event**

Di halaman tersebut receptionist dapat membuat event baru.

Contoh:

Nama Event:
`Training Karyawan Baru`

Tanggal:
`20 Agustus 2026`

Waktu:
`09:00 - 12:00`

Lokasi:
`Meeting Room 1`

Setelah event dibuat, event tersebut dapat dipilih ketika melakukan Quick Check-in.

---

# 4. PERUBAHAN QUICK CHECK-IN

Pada halaman Quick Check-in, tambahkan pilihan:

**Jenis Kunjungan:**

* Kunjungan Biasa
* Kunjungan Event

Jika memilih **Kunjungan Biasa**:

* Field Event tidak perlu diisi.
* `event_id = NULL`.

Jika memilih **Kunjungan Event**:

* Tampilkan dropdown daftar Event.
* Hanya tampilkan Event yang relevan/aktif sesuai tanggal dan statusnya.
* Receptionist wajib memilih Event.
* Simpan `event_id` pada data kunjungan.

Contoh:

Quick Check-in:

Nama Tamu:
`Budi`

Perusahaan:
`PT ABC`

Keperluan:
`Mengikuti training`

Jenis Kunjungan:
`Kunjungan Event`

Event:
`Training Karyawan Baru`

Kemudian ketika Check-in berhasil, data kunjungan terhubung ke event tersebut.

---

# 5. QUICK CHECK-OUT

Quick Check-out tetap menggunakan data kunjungan yang sama.

Jika kunjungan tersebut berasal dari Event:

* Check-out tetap dicatat pada record kunjungan.
* Event tidak boleh berubah.
* Waktu check-in dan check-out tetap tersimpan.
* Durasi kunjungan dapat dihitung.

Jangan membuat record baru hanya karena melakukan check-out.

Gunakan satu record kunjungan dari Check-in sampai Check-out.

---

# 6. RIWAYAT KUNJUNGAN

Pada halaman **Riwayat Kunjungan**, tambahkan kolom:

* Nama Tamu
* Perusahaan
* Bertemu Dengan
* Keperluan
* Event
* Check-in
* Check-out
* Status
* Durasi
* Dan kolom lain yang memang sudah ada.

Untuk kolom **Event**:

### Kunjungan biasa

Tampilkan:

`-`

### Kunjungan Event

Tampilkan:

`Nama Event`

Contoh:

| Tamu | Bertemu Dengan | Event                  | Check-in | Check-out |
| ---- | -------------- | ---------------------- | -------- | --------- |
| Budi | -              | -                      | 08:30    | 09:15     |
| Andi | -              | Training Karyawan Baru | 08:45    | 12:10     |
| Siti | Rudi           | -                      | 10:00    | 11:00     |

PENTING:

Pada Quick Check-in Event, kolom **Bertemu Dengan tidak harus diisi `-` karena event sudah menjadi konteks kunjungannya**.

Namun jika aplikasi memang tetap membutuhkan `Bertemu Dengan`, jangan menghapus field tersebut. Buat field tersebut optional untuk kunjungan event.

# 8. LAPORAN EVENT TERPISAH

Tambahkan halaman khusus:

**Laporan Event**

Halaman ini HARUS TERPISAH dari laporan kunjungan umum.

Tujuannya agar admin/receptionist dapat melihat performa dan data setiap event secara khusus.

Filter minimal:

* Event
* Tanggal
* Status Event
* Periode

Laporan dapat menampilkan:

* Total Event
* Total peserta
* Total yang sudah check-in
* Total yang sudah check-out
* Total yang masih berada di lokasi
* Rata-rata durasi kunjungan
* Event paling ramai
* Jumlah peserta per event
* Jumlah perusahaan per event

Jika aplikasi sudah memiliki fitur export laporan, laporan event juga harus dapat mengikuti mekanisme export yang sudah ada.

# 9. RELASI DATABASE

Jangan membuat desain database yang duplikatif.

Gunakan relasi:

**events**
→ memiliki banyak **visits**

**visits**
→ dapat memiliki satu **event**

Konsepnya:

`events.id`

direlasikan ke:

`visits.event_id`

`visits.event_id` harus nullable karena tidak semua kunjungan berasal dari event.

Contoh:

```text
events
------
id
name
description
event_date
start_time
end_time
location
status
created_by
created_at
updated_at

visits
------
id
visitor_id
employee_id
event_id NULL
purpose
check_in
check_out
status
created_at
updated_at
```

Sesuaikan nama tabel dan kolom dengan struktur database project yang SUDAH ADA.

JANGAN membuat tabel baru yang menduplikasi tabel `visits` atau `visitor`.

Receptionist:

* Bisa membuat Event

* Bisa melihat seluruh Event
* Bisa melihat laporan Event

* Tetap memiliki akses terhadap seluruh data kunjungan

* Bisa melihat Event
* Bisa melihat detail Event
* Bisa melihat laporan Event

Gunakan sistem permission/role yang SUDAH ADA. Jangan membuat sistem authorization baru kalau tidak diperlukan.

# 12. VALIDASI PENTING

Implementasikan validasi agar:

* Event tidak bisa dipilih jika sudah Cancelled.
* Event yang sudah Finished tidak bisa digunakan untuk check-in baru.
* Event harus sesuai dengan tanggal/waktu yang diperbolehkan.
* Receptionist tidak bisa menghubungkan kunjungan ke Event yang tidak valid.
* Check-out tetap menggunakan record kunjungan yang sama.
* Menghapus Event tidak boleh menyebabkan data historis kunjungan rusak.

Untuk data historis, lebih aman menggunakan soft delete/nonaktifkan Event jika struktur project mendukung.

# 13. UI/UX

Jangan membuat flow yang ribet.

Quick Check-in harus tetap cepat.

Flow:

```text
Quick Check-in
      ↓
Pilih Jenis Kunjungan
      ↓
 ┌─────────────────────┐
 │ Kunjungan Biasa     │
 │ Kunjungan Event     │
 └─────────────────────┘
      ↓
Jika Event
      ↓
Pilih Event
      ↓
Isi data tamu
      ↓
Check-in berhasil
```

Receptionist harus bisa melakukan Quick Check-in biasa tanpa dipaksa memilih Event.

Sebaliknya, jika memilih Kunjungan Event, pemilihan Event wajib dilakukan.

# HASIL AKHIR YANG DIINGINKAN

Konsep final aplikasi:

**Kunjungan**
→ bisa berupa **Kunjungan Biasa** atau **Kunjungan Event**

**Quick Check-in**
→ tetap cepat untuk kedua jenis kunjungan.

**Event**
→ dibuat oleh Receptionist dan memiliki data serta halaman sendiri.

**Riwayat Kunjungan**
→ tetap menjadi riwayat seluruh kunjungan, dengan informasi Event jika kunjungan tersebut terkait Event.

**Laporan Event**
→ menjadi laporan khusus untuk menganalisis peserta dan aktivitas setiap Event.

Jangan hanya menambahkan kolom Event di UI. Implementasikan Event sebagai entity/fitur yang benar-benar terintegrasi dengan alur Check-in, Check-out, Riwayat Kunjungan, dan Laporan.
